# 아키텍처 결정사항

> 새 기능을 만들 때 **woong-world 내부**에 넣을지, **별도 레포**로 뺄지 판단 기준

---

## 판단 기준표

| 기준 | 내부 앱 (path) | 외부 앱 (url + iframe) |
|------|---------------|----------------------|
| 기능 크기 | 가벼움 (Todo 수준) | 무거움 (자체 DB, AI, 백엔드) |
| 배포 독립성 | woong-world와 함께 배포 | 독립 배포, 독립 장애 격리 |
| 코드 결합도 | 높음 (공유 컴포넌트 가능) | 낮음 (API 경계만 공유) |
| 개발 속도 | 빠름 (기존 스택 그대로) | 느림 (세팅 별도 필요) |
| 언제 선택? | UI 위젯, 간단한 CRUD | 자체 서버 로직, 무거운 AI 처리 |

---

## 결정 이력

### 주식 자동매매봇 → **외부 앱**
- 이유: 이미 별도 레포 존재. 매매 엔진은 woong-world와 분리된 서버 필요.
- 방식: 기존 레포 Vercel 배포 → `url` 등록 → iframe embed
- 참고: [[03 주식 자동매매봇]]

### VFX 어시스턴트 → **외부 앱**
- 이유: 프롬프트 라이브러리, AI 변환 등 자체 기능이 독립적으로 커질 가능성.
  woong-world 빌드 시간을 늘리지 않기 위해 분리.
- 방식: `il-oong/vfx-assistant` 신규 레포 → Vercel 배포 → `url` 등록
- 참고: [[04 VFX 어시스턴트]]

## 무거운 플러그인 여럿 들어갔을 때 woong-world는?

woong-world 자체는 **거의 영향 없음**.  
iframe 태그 하나만 추가되는 구조라서 외부 앱이 느려도 woong-world는 가볍게 유지됨.

부담이 생기는 시나리오:
- 플러그인 CI 상태를 매 로드마다 GitHub API로 조회할 때 → rate limit
  → 해결: `GITHUB_TOKEN` 필수 설정, Redis에 상태 캐싱 (TTL 5분)

- 기존 데이터를 읽어 보여주는 뷰
- 전역 AI 어시스턴트 컨텍스트 확장
